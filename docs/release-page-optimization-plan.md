# 发布页面优化方案（Release Page Optimization Plan）

> 更新时间：2026-09-01  
> 适用页面：`frontend/src/pages/Release/components/FlowWorkspace/index.tsx`、`frontend/src/pages/Release/components/ReleaseFlow/index.tsx`、`frontend/src/pages/Release/components/ReleaseWizard/index.tsx`、`frontend/src/pages/Release/orderDetail/index.tsx`  
> 目标：把当前“流程完整但信息量大”的发布页，升级为一套**可理解、可决策、可追溯、可回滚**的发布工作台。

---

## 1. 先给结论

现在的发布页，已经具备完整的发布能力：

- 草稿创建
- 契约检查
- 回归评测
- 灰度放量
- 全量上线
- 回滚 / 终止
- 历史记录
- 门禁结果
- 发布单详情

**问题不在能力，而在“表达方式”和“流程组织方式”。**

它目前更像一个“发布控制台”，而不是一个“发布决策界面”。

### 当前最明显的 5 个问题

1. **流程很多，但主次不清**  
   用户看到的是一串动作，不是一条清晰的决策路径。
2. **信息很全，但阅读成本高**  
   契约、回归、Canary、版本、记录、门禁混在同一层。
3. **按钮很多，但 CTA 不统一**  
   同一屏上同时存在多个可执行动作，容易分散注意力。
4. **失败信息不够“决策化”**  
   用户知道“错了”，但不够清楚“下一步该做什么”。
5. **发布像工程动作，不像产品动作**  
   缺少“这次为什么发、发什么、风险是什么、成功后会怎样”的完整叙事。

### 一句话判断

**当前发布页已经能完成流程，但还没有把“发布决策”产品化。**

---

## 2. 发布流程的产品定位

发布不是一个按钮，而是一条闭环：

> **准备版本 → 校验风险 → 进入灰度 → 观察指标 → 决定全量 / 回滚 → 归档复盘**

也就是说，发布页要同时回答五个问题：

1. 这次能不能发？
2. 如果不能发，卡在哪里？
3. 如果强制发，代价是什么？
4. 发出去之后我看什么？
5. 出问题后怎么回滚？

如果用户不能在短时间内回答这五个问题，发布页就还停留在“控制台阶段”。

---

## 3. 竞品 / 成熟产品的通用做法

这里不看按钮数量，而看成熟产品如何组织“发布前-发布中-发布后”的决策链路。

### 3.1 质量门禁要先摘要、后细节

成熟的发布流程通常会先给一个**总结果**，再展开看详细检查项。这样用户先知道“能不能发”，再看“为什么”。

**可借鉴点：**
- 先展示门禁总状态，再展开检查明细
- 把失败项聚合成原因摘要，不要让用户自己拼图
- 不同严重等级的阻断项，要有不同视觉表达

### 3.2 发布动作要“单主按钮”

用户在发布页上最需要的是“当前阶段下一步是什么”。优秀的流程页通常每个阶段只有一个最重要的按钮，其他按钮都降级。

**可借鉴点：**
- 每个阶段保留一个主 CTA
- 风险动作必须有解释与确认
- 低频动作收纳到更多菜单或二级面板

### 3.3 结果对比要围绕“变化”而不是“罗列”

发布不是看一堆数字，而是看“这次和上次相比变了什么”。因此版本差异、指标变化、回归变化、风险变化都应聚焦在差异上。

**可借鉴点：**
- 当前版本 vs 上一稳定版本
- diff 视图比纯列表更有决策价值
- 重点高亮“退化项”和“新增风险项”

### 3.4 预览比执行更重要

在真正执行发布前，用户需要知道会发生什么：是否会进入灰度、是否会触发回滚、是否会影响哪些指标。

**可借鉴点：**
- 发布前给出可预期结果
- 高风险操作需要明确影响范围
- 预览要能直接帮助用户做“要不要继续”的判断

### 3.5 结果页要能复盘

发布完成后，用户不是只想看“成功”两个字，而是想知道：

- 成功到什么状态
- 灰度有没有问题
- 是否需要继续放量
- 如果出问题，谁来处理

**可借鉴点：**
- 每次发布都能回到同一份发布单
- 发布记录、门禁记录、灰度记录、回滚记录要串起来
- 发布完成后要给出下一步建议

## 4. 当前页面的结构诊断

### 4.1 FlowWorkspace：总览页过于“信息拼装”

`FlowWorkspace` 现在承担了：

- 版本列表
- 发布流总览
- 门禁结果展示
- 历史记录
- 发布向导入口
- 灰度 / 全量 / 回滚动作

这些功能都合理，但放在一起时容易出现一个问题：**用户不知道先看哪个、先点哪个。**

#### 改造目标

总览页应该承担三件事：

1. 告诉用户当前处于哪一阶段
2. 告诉用户下一步应该做什么
3. 告诉用户当前风险是什么

而不是把所有历史和操作都平铺出来。

---

### 4.2 ReleaseFlow：适合做“发布看板”，不适合继续承载全部细节

`ReleaseFlow` 已经包含很多信息：

- 草稿 / 契约 / 回归 / 灰度 / 全量五阶段
- 状态与历史
- 门禁结果
- 检查记录
- Canary 状态
- 发布 / 回滚 / 终止动作

这很强，但也说明它已经接近“控制台上限”。再继续加内容，只会更重。

#### 建议定位

把 `ReleaseFlow` 定位为：

- **发布总览 + 阶段状态板 + 关键动作入口**

而不是：

- 既是总览，又是详单，又是引导，又是复盘台

---

### 4.3 ReleaseWizard：应该成为“发布决策助手”，不是“按钮串联器”

当前 Wizard 已经有 4 个步骤：

1. 兼容性检查
2. 回归验证
3. 发布
4. 灰度放量

问题是：**步骤本身是对的，但每步的解释还可以更产品化。**

#### 现状问题

- 用户需要自己理解版本、门禁、force、灰度之间的关系
- “下一步”按钮的语义弱于“当前阶段要做什么”
- 失败后虽然能看到错误，但没有“建议动作”
- 强制发布（force）可用，但心智上太像技术开关

---

### 4.4 发布单详情页：应该成为“发布真相页”

`orderDetail` 这类页面不应该只是历史详情，而应承担“单次发布的事实归档”角色。

#### 它应回答

- 谁发的
- 发了什么版本
- 经过了哪些检查
- 灰度发生了什么
- 为什么最终上线 / 回滚
- 后续是否还有风险

#### 这页最重要的价值

不是展示更多字段，而是把一次发布的所有关键事实串成完整故事。

---

## 5. 我会怎么改：产品目标

### 5.1 三个目标

1. **让用户一眼知道现在能不能发**
2. **让用户清楚知道为什么能 / 不能发**
3. **让用户在发布后能快速复盘和回滚**

### 5.2 一句话定位

把发布页从：

> “我来点按钮完成发布”

升级成：

> “我来确认风险、批准发布、观察结果、必要时快速回退”

---

## 6. 发布全流程的推荐状态模型

建议把发布流程统一成一套状态机，避免页面与流程的语义漂移。

### 6.1 核心状态

| 状态 | 含义 | 用户最关心的问题 |
|---|---|---|
| `DRAFT` | 草稿已创建，尚未验证 | 这版本准备好了吗 |
| `CONTRACT` | 正在做契约检查 | 有没有结构性问题 |
| `REGRESSION` | 正在做回归评测 | 质量是否退化 |
| `GRAY` | 进入灰度观察 | 线上稳定吗 |
| `ACTIVE` | 已全量上线 | 能不能继续保持 |
| `DISABLED` | 已停用 / 回滚 | 为什么回滚了 |
| `TERMINATED` | 流程被终止 | 这次发布还继续吗 |

### 6.2 决策状态

除了阶段状态，还要有决策状态：

- **可继续**：当前阶段可以进入下一步
- **需人工确认**：存在风险，但允许强制继续
- **阻断**：必须先修复，再继续
- **观察中**：灰度中，需要等待指标稳定
- **已回滚**：本次发布结束，等待复盘

### 6.3 设计原则

- 阶段状态负责“进度”
- 决策状态负责“是否能走下一步”
- 不能把两者混成一回事

---

## 7. 发布流程的推荐结构

建议把发布页拆成 4 层：

### 7.1 顶层：当前发布摘要

只回答三件事：

- 当前版本是谁
- 当前阶段在哪
- 当前风险是什么

### 7.2 中层：下一步动作

只放当前阶段最重要的一件事：

- 草稿阶段：运行契约检查
- 契约通过阶段：运行回归评测
- 回归通过阶段：确认发布
- 灰度阶段：继续放量 / 暂停 / 回滚

### 7.3 证据层：门禁 / diff / Canary

只展示决策所需证据：

- 契约检查结果
- 回归结果
- 当前版本 diff
- 灰度指标
- 失败原因聚合

### 7.4 追溯层：历史 / 审计 / 发布单详情

用于复盘和定位问题：

- 谁执行了什么动作
- 什么时候执行的
- 为什么执行 / 为什么失败
- 是否已经回滚

## 8. 发布页优化方案

### 8.1 总览页重构：从“功能集合”改成“决策面板”

建议将发布页主结构收敛为 4 个区域：

1. **发布状态卡**
   - 当前版本
   - 当前阶段
   - 风险等级
   - 是否可发布
   - 上一次成功时间

2. **下一步动作卡**
   - 下一步应该做什么
   - 这个动作的前置条件
   - 如果失败会怎样

3. **门禁摘要卡**
   - 契约检查结果
   - 回归结果
   - Canary 摘要
   - 失败原因聚合

4. **版本与历史区**
   - 当前版本列表
   - 历史发布记录
   - 回滚入口

#### 设计原则

- 总览页先给结论，再给证据
- 发布动作和复盘动作分开
- 不要把所有细节都平铺在首屏

---

### 8.2 门禁结果表达优化

#### 当前问题

- 检查项多，但用户需要自己理解严重度
- 阻断、警告、建议修复的边界不够清晰
- 失败原因可以看，但不够聚合

#### 建议改法

1. **门禁总结果优先**
   - pass / warn / block 三态明显区分

2. **失败项聚合**
   - 相同类型的失败项合并显示
   - 默认只显示前 3 个关键失败原因

3. **建议动作**
   - 每个失败原因后增加“建议修复动作”
   - 例如：补测、回滚、修改 prompt、补充评测集

4. **人工签核单独显示**
   - `needs_manual` 这类项不要混在 pass/fail 列表里
   - 单独成为“需要人工确认”的信息块

5. **阻断原因可追责**
   - 显示阻断来源：契约 / 回归 / 人工审批 / Canary
   - 方便后续复盘和责任定位

---

### 8.3 版本差异视图

发布页非常需要一个“变化视图”，否则用户很难判断这次发布到底值不值得。

#### 建议增加的差异维度

- system prompt diff
- model diff
- config diff
- 评测集差异
- 门禁结果差异
- Canary 指标差异

#### 视觉建议

- 只高亮变化项，不重复展示没变的字段
- 变化项分为“新增 / 删除 / 修改 / 风险增加”
- 如果当前版本与上一稳定版本差异太大，给出风险提示

---

### 8.4 CTA 层级重排

建议每个阶段只有一个最强动作。

#### 阶段建议

- **草稿阶段**：`运行契约检查`
- **契约通过阶段**：`运行回归评测`
- **回归通过阶段**：`确认发布`
- **灰度阶段**：`继续放量` 或 `暂停 / 回滚`

#### 次级动作

- 查看详情
- 查看历史
- 导出报告
- 终止流程

#### 危险动作

- 强制发布
- 回滚
- 终止

危险动作必须：

- 更明显的视觉提示
- 二次确认
- 明确说明后果

---

### 8.5 失败与阻断的文案优化

当前错误文案的目标应该从“告诉你错了”变成“告诉你怎么处理”。

#### 文案结构建议

每条失败提示最好包含：

1. 发生了什么
2. 为什么阻断
3. 应该先做什么
4. 是否允许继续

#### 示例结构

- `回归未通过：本次通过率低于上一版本，发布被阻断。`
- `建议先检查退化案例，再重新运行回归。`
- `如果确认是误判，可在人工签核后继续。`

---

### 8.6 灰度阶段优化

灰度阶段是发布页的关键决策点，建议单独强化。

#### 当前要解决的问题

- 灰度百分比只是一个输入项
- 用户不容易判断这个比例是否合理
- 灰度中的监控信息不够显眼

#### 优化方向

- 提供推荐灰度比例模板：1%、5%、10%、25%
- 提示“当前灰度策略是否偏保守 / 激进”
- 灰度后重点展示 Canary 指标：错误率、延迟、成本、成功率
- 当 Canary 恶化时，给出明确回滚建议
- 提供“一键暂停观察”入口，避免只能在继续 / 回滚之间二选一

---

### 8.7 历史记录与复盘

发布不是一次性动作，而是可追溯的过程。

#### 建议补齐的复盘信息

- 谁发的
- 什么时候发的
- 发了什么版本
- 经过了哪些门禁
- 灰度结果如何
- 最终是否回滚
- 回滚原因是什么
- 是否触发人工签核

#### 建议交互

- 历史记录默认按时间线显示
- 支持筛选“成功 / 失败 / 回滚 / 终止 / 强制发布”
- 单次发布支持导出报告
- 支持从历史记录一键回到对应版本草稿

---

## 9. ReleaseWizard 优化方案

### 9.1 Wizard 的角色重新定义

它应该是：

> 一个帮助用户完成“选择版本 → 检查风险 → 决定发布 → 观察结果”的引导器

而不是：

> 一个把多个按钮串成四步的表单弹窗

### 9.2 步骤建议

建议保留 4 步，但每一步都要有明确任务和结果。

#### Step 1：选择版本

- 显示版本号、状态、最近修改信息
- 显示与当前线上版本的关键差异
- 默认选中最新可发版本
- 如果没有可发版本，直接提示“先创建草稿”

#### Step 2：契约检查

- 先给总结果，再给检查明细
- 阻断项置顶
- 每个失败项给建议动作
- 对于 `needs_manual` 给出人工签核说明

#### Step 3：回归评测

- 展示对比基线和退化幅度
- 显示是否满足最低通过标准
- 支持查看失败样本
- 说明回归失败是否允许强制继续

#### Step 4：发布 / 灰度

- 显示确认摘要
- 给出推荐灰度比例
- 执行后直接跳到结果页或回到总览页
- 发布成功后提示“下一步去看什么”

### 9.3 强制发布（force）的产品化

`force` 是高风险能力，不能像普通 checkbox 一样太轻。

#### 建议

- 不默认勾选
- 勾选前展示影响说明
- 需要输入确认语句或二次验证
- 在审计里明确记录“谁在什么理由下强制发布”

#### 文案建议

把“强制发布”改成更明确的表达：

- `我已确认风险，仍要继续`
- `确认忽略本次阻断门禁`

这样比纯技术词更适合产品界面。

### 9.4 发布完成后的反馈

发布成功后不应只是一个成功提示，而应提供下一步。

#### 推荐完成页内容

- 已发布到哪个状态
- 下一步去哪里看灰度结果
- 是否需要继续放量
- 是否需要查看历史

#### 可选动作

- 查看发布详情
- 查看回归报告
- 进入灰度监控
- 复制本次发布摘要

## 10. 发布单详情页优化方案

### 10.1 详情页的定位

发布单详情页不是“额外的一页”，而是发布流程的“真相归档页”。

它要回答：

- 这次到底发生了什么
- 哪一步成功，哪一步失败
- 为什么最后成功 / 回滚
- 以后类似问题如何更快处理

### 10.2 建议结构

#### 顶部：发布摘要

- 版本号
- 当前状态
- 执行人
- 发起时间
- 当前风险等级

#### 中部：时间线

按时间顺序展示：

- 创建草稿
- 契约检查
- 回归评测
- 灰度开始
- Canary 变化
- 全量上线 / 回滚 / 终止

#### 右侧 / 底部：证据附件

- 检查结果
- 指标快照
- 失败原因
- 审计记录
- 导出报告

### 10.3 详情页的核心价值

- 让“为什么发布/为什么回滚”可解释
- 让“谁决定的”可追溯
- 让“以后怎么避免”可复盘

## 11. 我会怎么落地到前端代码

## 13. 指标与监控建议

发布页优化不是只看“好不好看”，更要看“决策是否更快、更稳”。

### 13.1 核心指标

| 指标 | 说明 | 目标 |
|---|---|---|
| 发布成功率 | 从发起到最终上线的成功比例 | 稳定提升 |
| 门禁阻断率 | 被 contract / regression 阻断的比例 | 能看懂、能解释 |
| 灰度回滚率 | 灰度阶段触发回滚的比例 | 越低越好 |
| 人工签核触发率 | 需要人工确认的占比 | 保持可控 |
| 平均发布时长 | 从草稿到上线的耗时 | 下降 |
| 详情页访问率 | 发布后是否有复盘 | 上升 |
| 强制发布使用率 | force 的使用频率 | 保持低频且可审计 |

### 13.2 交互指标

- 用户是否经常点击“查看详情”
- 用户是否经常在灰度阶段停留
- 用户是否频繁使用“回滚”而不是“继续”
- 用户是否在门禁失败后成功修复并重试

- 发布完成到下次操作的转化率

## 15. 验收标准

如果发布页优化到位，用户应该能快速回答以下问题：

1. **这次能不能发？**
2. **如果不能发，卡在哪里？**
3. **如果强制发，代价是什么？**
4. **发出去之后我看什么？**
5. **出问题后怎么回滚？**

只要这五个问题能在 30 秒内被用户看懂，发布页就从“控制台”进化成了“产品化发布工作台”。
