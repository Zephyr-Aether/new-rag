# Onboarding Wizard 优化方案（Onboarding Wizard Optimization Plan）

> 更新时间：2026-09-01  
> 适用页面：`frontend/src/components/Onboarding/index.tsx`、`frontend/src/pages/ConfigCenter/index.tsx`、`frontend/src/pages/Users/index.tsx`  
> 目标：把当前“能跑通第一条链路”的引导，升级成“低门槛、低认知、可跳过、可恢复”的首次成功路径。

---

## 1. 先给结论

现在的 Onboarding Wizard 已经能帮助用户完成首次价值路径：

- 选场景
- 接模型
- 导入示例知识
- 跑问题
- 去发布治理

这个方向是对的。**当前最大的问题不是流程缺失，而是“首次价值”和“长期使用”还没有完全分开。**

### 当前最明显的 5 个问题

1. **步骤很完整，但认知成本仍偏高**：用户需要先理解场景、模型、知识库、问答、发布之间的关系。
2. **示例很有用，但还不够“自动化”**：用户仍然需要做一些判断和手动操作。
3. **对不同用户类型没有明显分流**：管理员、实施、产品、普通使用者看到的引导应该不同。
4. **完成后没有足够强的“下一步建议”**：用户跑通后，应该明确知道接下来去哪里。
5. **跳过/返回/继续的容错还可以更好**：首次引导最好是“可中断、可恢复、可重复”。

### 一句话判断

**这套 Wizard 的方向已经正确，下一步重点是降低认知负担、提高自动化程度、强化结果反馈。**

---

## 2. 竞品/成熟产品的引导共性

Onboarding 做得好的产品，通常不是“把功能讲一遍”，而是“让用户尽快完成一次成功”。

### 2.1 首次成功比完整介绍更重要

成熟产品通常会优先设计一个最小可成功路径，而不是把所有能力一次性展示给用户。

**可借鉴点：**
- 先让用户完成一个真实但简单的任务
- 不要一开始就要求用户理解所有模块
- 第一轮成功后再渐进展示高级能力

### 2.2 模板比空白表单更重要

首次使用时，用户最怕的是“我该填什么”。优秀产品会直接给模板、范例、预设场景。

**可借鉴点：**
- 场景模板优先于自由配置
- 示例文档优先于空知识库
- 预设问题优先于让用户自己想 prompt

### 2.3 进度可见比页面跳转更重要

用户在 onboarding 中最需要的是“我现在做到哪一步了、还差什么、多久能完成”。

**可借鉴点：**
- 明确的步骤条
- 每步完成反馈
- 估时和完成率
- 失败后的回退与重试

### 2.4 跳过并不等于放弃

好的 onboarding 允许用户跳过，但会保留下一次回来继续的路径。

**可借鉴点：**
- 能跳过
- 能稍后继续
- 能从任意步骤重新进入
- 能根据已有状态自动跳过重复步骤

---

## 3. 当前流程诊断

### 3.1 当前的设计思路

当前 Wizard 的路径是：

1. 选场景
2. 接模型
3. 导入样例
4. 运行示例问题
5. 去发布治理

这个链路非常适合企业 Agent 平台，因为它直接把“第一次成功”的闭环串起来了。

### 3.2 当前的优点

- 有明确目标：跑通第一次价值
- 有真实动作：创建知识库、导入文档、创建 run
- 有结果出口：能直接去看执行详情或发布页
- 不只是讲概念，而是真的带用户操作

### 3.3 当前的主要短板

- 场景选择和实际价值之间的映射还可以更强
- 模型接入这一步对新手来说略抽象
- 导入样例时，用户很容易把它当成“演示”而不是“真实可复用模板”
- 运行问题后，缺少更明确的“成功说明”和“下一步建议”

---

## 4. 我会怎么改：产品目标

### 4.1 三个目标

1. **让用户在最短时间看到第一次结果**
2. **让用户知道这套产品到底能帮他解决什么**
3. **让用户完成一次成功后自然进入主页面**

### 4.2 一句话定位

把 Onboarding 从：

> “教用户怎么用系统”

改成：

> “帮用户快速完成一次真实业务成功”

---

## 5. 详细优化方案

## 5.1 入口策略优化

### 当前问题

现在的 onboarding 更像一个“弹窗式流程”，但没有很好地区分：

- 新用户第一次进入
- 已有配置但没跑通
- 老用户需要重新体验
- 管理员替别人初始化环境

### 建议

1. **首次进入自动提示，但不强制**
   - 用轻量 banner / card 提醒
   - 明确说明“3 分钟跑通第一次价值”

2. **根据状态智能判断是否弹出**
   - 已有模型、已有知识库、已有 run 的用户，不要每次都默认打断
   - 对已完成过引导的用户，改成“再次查看引导”入口

3. **提供明确的重新开始入口**
   - `重新体验 onboarding`
   - `跳过并进入首页`
   - `稍后继续`

---

## 5.2 场景选择优化

当前第一步是选场景，这一步非常关键，因为它决定了后续样例内容是否有代入感。

### 问题

- 场景卡片有，但场景与业务价值的关系还可以更明确
- 用户可能只看到“卡片标题”，看不到“选它会带来什么”

### 优化建议

1. **每个场景卡片增加“适用对象”**
   - 例如：客服、运营、HR、产品、售后、实施

2. **增加“完成后会得到什么”**
   - 比如：示例知识库、示例问答、示例发布路径

3. **默认推荐一个场景**
   - 如果没有用户输入，则自动推荐最通用场景

4. **允许用户自定义场景标题**
   - 适合更贴近真实业务

---

## 5.3 模型接入步骤优化

### 当前问题

这一页在概念上很重要，但对新用户来说，容易从“产品引导”变成“配置理解”。

### 建议

1. **把“真实模型 / 模拟模型”说得更直白**
   - 说明当前体验模式
   - 明确告诉用户“先走通，再切真实模型”

2. **自动检测现有配置**
   - 已有模型配置则直接展示已接入状态
   - 没有配置则给出最短配置路径

3. **把配置动作前置到主路径之外**
   - wizard 里默认不强逼配置完再继续
   - 先能跑通，再引导去配置中心完善

4. **强化“可选”语义**
   - 真实模型接入可选，但不是阻塞项
   - 让用户先获得成功感

---

## 5.4 示例知识库步骤优化

这是 onboarding 的核心步骤之一。

### 问题

现在的示例知识库创建很有价值，但用户可能只会把它理解成演示样例，而不是“可复用模板”。

### 建议

1. **把示例明确叫做“可复用模板”**
   - 让用户知道这不是一次性 demo

2. **展示知识库会包含什么**
   - 文档标题、内容类型、适用场景

3. **展示导入后的可见结果**
   - 例如：文档已入库、可检索、可引用

4. **导入成功后给一个“立刻验证”按钮**
   - 让用户在下一步马上验证效果

5. **支持使用已有知识库跳过这一步**
   - 对已经有业务数据的用户，不应该重复造示例库

---

## 5.5 示例问题运行步骤优化

这是“第一次成功”的关键瞬间。

### 问题

现在的运行问题已经能直接创建 run，但用户要知道：

- 为什么问这个问题
- 为什么这个答案算成功
- 答案的可信度从哪里来

### 建议

1. **明确示例问题的目的**
   - 不是为了演示对话，而是为了验证知识是否生效

2. **成功后展示三件事**
   - 回答结果
   - 引用来源
   - 执行轨迹 / run 链接

3. **把结果与下一步连接起来**
   - 如果答案靠谱，下一步就是去发布治理
   - 如果答案不靠谱，下一步就是返回知识库或模型接入

4. **失败时给修复建议**
   - 没命中知识：去看导入是否成功
   - 模型异常：去检查模型配置
   - 答案不稳定：去做回归评测

---

## 5.6 完成页优化

用户完成 onboarding 后，不能只是关掉弹窗，而应该得到一个明确的“完成结果页”。

### 建议展示内容

- 你已经完成了什么
- 当前环境里已经有哪些资源
- 下一步最值得做什么
- 是否要去发布第一个版本

### 推荐 CTA

- `进入工作台`
- `去发布第一个版本`
- `再看一遍引导`
- `继续完善知识库`

### 完成后的心智目标

让用户觉得：

> “我已经把产品跑起来了，接下来我知道去哪。”

---

## 5.7 跳过与恢复策略

### 当前问题

如果 onboarding 对用户是打断式体验，就必须保证它不会造成“退出后找不回来”的问题。

### 建议

1. **随时跳过**
   - 跳过时不应该让用户丢失环境

2. **随时重新进入**
   - 首页、设置页、工作台都能再次打开

3. **记录完成状态**
   - 已完成、已部分完成、未开始

4. **支持从断点继续**
   - 如果用户中断在某一步，再进来时应回到上次位置

---

## 5.8 个性化优化

不同角色看到的 onboarding 应该不同。

### 建议分层

- **管理员**：先看租户、用户、模型接入、知识库、发布治理
- **实施/交付**：先看环境准备、示例导入、首次成功、回滚路径
- **业务使用者**：先看提问、引用来源、结果可信度
- **产品/运营**：先看评测、反馈、发布节奏

### 好处

- 少讲无关内容
- 每个角色都更快感到“这就是给我准备的”

---

## 6. 建议的流程重排

### 推荐顺序

1. 选场景
2. 识别现有环境（模型 / 知识库 / 权限）
3. 自动创建或选择示例知识
4. 跑第一条示例问题
5. 查看结果与引用
6. 跳到发布或工作台

### 为什么这样排

因为它符合用户的心理顺序：

- 先知道“这是什么”
- 再看到“我现在哪里”
- 然后做“一个最小成功动作”
- 最后才进入更复杂的治理流程

---

## 7. 对现有代码的建议改造点

### 7.1 优先改这些文件

- `frontend/src/components/Onboarding/index.tsx`
  - 优化步骤文案
  - 增加状态判断
  - 改善完成页与跳过策略

- `frontend/src/pages/ConfigCenter/index.tsx`
  - 增加 onboarding 入口
  - 配置中心与引导流程互相联动

- `frontend/src/pages/Users/index.tsx`
  - 在租户 onboarding 场景里提供更明确的初始化入口

### 7.2 不建议先做的事

- 不要先把 wizard 做得更复杂
- 不要先加更多必填项
- 不要一上来就要求用户完成所有配置
- 不要把 onboarding 变成“产品说明书”

应该优先的是：

**先让用户成功，再让用户理解。**

---

## 8. 实施优先级

### P0：减少首次理解成本

- 明确步骤目标
- 强化场景选择
- 强化完成后的下一步
- 跳过/继续更清楚

### P1：提升自动化

- 自动识别已有配置
- 自动跳过已完成步骤
- 自动生成或复用示例资源
- 结果页更完整

### P2：按角色个性化

- 管理员版
- 实施版
- 业务版
- 产品版

### P3：指标闭环

- 打开率
- 完成率
- 中途流失率
- 从 onboarding 到首条 run 的转化率
- 从 onboarding 到首次发布的转化率

---

## 9. 验收标准

如果 Onboarding 优化到位，用户应该能快速回答以下问题：

1. **我该从哪里开始？**
2. **现在做这一步是为了什么？**
3. **我已经成功了吗？**
4. **下一步该去哪里？**
5. **我能不能随时回来继续？**

只要这五个问题能在页面里被清楚回答，Onboarding 就不只是“引导”，而是真正的“首次成功路径”。
