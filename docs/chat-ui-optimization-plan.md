# 聊天框 UI 优化计划（Chat UI Optimization Plan）

> 更新时间：2026-09-01  
> 范围：`frontend/src/pages/Chat/index.tsx`、`frontend/src/pages/Chat/components/MessageBubble/index.tsx`、`frontend/src/styles.less`  
> 目标：把当前“功能齐全但偏控制台”的聊天页，升级成“聊天优先、信息分层清晰、操作更顺手”的产品级体验。

---

## 1. 先给结论

从产品和设计的角度看，这个聊天页 **不是功能差，而是层级太重、主次不够清楚**。

它现在更像一个“能工作的 Agent Ops 控制台”，而不是一个“让用户愿意持续对话、持续追问、持续复用”的聊天产品。

### 目前最明显的 5 个问题

1. **聊天不是绝对主角**：左侧会话、顶部流程、右侧验证信息、底部输入框同时抢注意力。
2. **信息密度偏高**：很多操作信息和结果信息以同等视觉权重出现，造成阅读负担。
3. **输入框不够“强”**：composer 有功能，但缺少明显的“开始对话”心智锚点。
4. **消息区还不够内容化**：助手回复、工具调用、引用来源的组织方式偏工程化。
5. **辅助面板没有做渐进披露**：验证信息很有价值，但不应该默认和正文并列同权。

### 一句话判断

**现在的 UI 能用，但离“产品感”还有一段距离。**
真正要优化的，不是再堆功能，而是把“聊天主路径”重新扶正。

---

## 2. 竞品是怎么做的

这里不做“抄外观”，只看成熟产品的通用设计策略：**主任务优先、辅助信息收纳、结构化内容独立呈现**。

### 2.1 ChatGPT：把上下文当作“工作区”而不是孤立对话

OpenAI 的 Projects 思路是把聊天、文件、说明一起放进一个持续工作的上下文空间里，强调“保持上下文连续”，而不是让用户每次重新开始。

**可借鉴点：**
- 把“会话”视为长期工作单元，而不是一次性消息列表
- 文件、说明、聊天记录要能共同服务同一目标
- composer 里把“上传/工具/知识”做成自然入口，而不是额外负担

参考：
- OpenAI Help Center: [Projects in ChatGPT](https://help.openai.com/en/articles/10169521)
- OpenAI Help Center: [File storage and Library in ChatGPT](https://help.openai.com/en/articles/20001052)
- OpenAI: [Working with files in ChatGPT](https://openai.com/academy/working-with-files/)

### 2.2 Claude：把“成品内容”从聊天里抽出来

Claude 的 Artifacts 很典型：当内容变成了“可复用的结果”，它会在右侧独立窗口展示，让主聊天继续保持对话节奏。

**可借鉴点：**
- 大段正文、代码、图表、可交付物，不要都塞在聊天气泡里
- 把结构化输出做成独立承载区
- 聊天负责“互动”，右侧负责“结果/编辑/复用”

参考：
- Anthropic Help Center: [What are artifacts and how do I use them?](https://support.anthropic.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them)
- Anthropic Help Center: [Intro to Artifacts](https://support.anthropic.com/en/articles/9945615-intro-to-artifacts)
- Anthropic Help Center: [Enabling and Using Web Search](https://support.anthropic.com/en/articles/10684626-enabling-and-using-web-search)

### 2.3 Cursor：主对话 + 侧对话，避免主线程被打断

Cursor 的 Side Chats 很适合这类“主任务 + 旁路分析”的场景。它把探索性问题拆到侧边，避免把主对话冲散，同时又保留上下文关联。

**可借鉴点：**
- 主聊天只服务主路径
- 复杂信息拆成“侧聊 / 侧栏 / 二级面板”
- 子任务结果可回流，但不要污染主线

参考：
- Cursor Docs: [Side chats](https://prod.cursor.com/help/ai-features/side-chats)
- Cursor Docs: [Cursor – Overview](https://docs.cursor.com/chat/overview)
- Cursor Docs: [@Files & Folders](https://docs.cursor.com/context/%40-symbols/%40-files-and-folders)

### 2.4 从竞品里提炼出的 4 个共性

1. **聊天区是第一视觉中心**
2. **辅助面板默认是二级信息**
3. **结构化结果会被独立承载**
4. **输入区要非常明确，降低开始成本**

## 3. 当前页面的设计诊断

### 3.1 布局层级问题：太像“工作台”，不像“对话页”

当前页面至少同时承载了 5 种信息层：

- 站点导航
- 会话列表
- 消息流
- 验证/工具/引用侧栏
- 顶部流程条

这些信息都合理，但它们的**视觉权重过于接近**，导致用户不知道先看哪里。

#### 具体表现

- 左右栏都很明确，但中间消息没有形成“绝对主场”
- 顶部流程和消息内容之间没有足够的主次差异
- 右侧验证信息与正文同屏同权，容易让用户把它看成“另一块主内容”
- 底部输入框面积不小，但缺乏“启动对话”的引导感

#### 产品后果

- 用户进入页面后，要先做“理解页面”这件事
- 不是一眼开始聊，而是先判断“这里该从哪下手”
- 这会显著拉高首次使用成本

---

### 3.2 会话列表问题：太像管理列表，不够像“聊天目录”

当前会话列表的问题不是“功能少”，而是“呈现方式过硬”。

#### 现在的感受

- 更像控制台里的资源列表
- 会话之间缺少层级和情绪差异
- 当前选中态、hover 态、空态、删除态等还可以更细腻

#### 建议方向

- 每个会话卡片只保留 3 个核心信息：标题、摘要、时间
- 当前会话高亮更明确，和普通项形成更清晰的对比
- 常用操作（重命名、置顶、归档、删除）收纳到 hover 菜单里，减少列表噪音
- 搜索框、置顶、归档、筛选做成统一的会话管理区

---

### 3.3 消息区问题：有内容，但阅读节奏还不够顺

消息区目前已经有 Markdown、代码块、工具折叠、引用来源等能力，这很不错。但问题在于：**这些能力没有被更像“内容产品”的方式组织起来**。

#### 具体问题

1. **助手回复太像一大段正文**，缺少节奏分组
2. **工具调用/引用来源** 虽然可折叠，但默认视觉权重仍偏高
3. **长回复的排版还可以更像“文档阅读”**，而不是“聊天文本”
4. **消息之间的留白与节奏感** 还可以更统一

#### 建议方向

- assistant 消息采用“卡片化正文 + 元信息分层”
- 代码块、引用、工具结果使用更明确的容器样式
- 长答案默认保留良好的行宽和段落节奏
- 工具调用与引用来源改为“摘要默认展开，细节点击展开”

---

### 3.4 Composer 问题：能发消息，但不够“有开始感”

输入区是聊天产品最关键的地方之一。现在它能用，但还没形成很强的“行动入口”。

#### 目前的主要问题

- 输入区域的存在感不够强
- 附件、发送、停止等动作的层级还可以更清晰
- 快捷提示存在，但和真正的输入动作绑定不够强
- 空状态时，没有形成足够明确的第一步引导

#### 建议方向

- 把 composer 做成更强的浮层卡片或底部固定操作区
- 输入框 focus 时强化边框/阴影/背景层
- 发送按钮更明确，主按钮优先级高于次级操作
- 附件、模板 prompt、快捷命令以“辅助入口”呈现，避免抢占主操作
- 空会话状态给出明显的推荐入口：试一条示例问题、上传文件、选择知识库

---

### 3.5 右侧验证面板问题：有价值，但太“平铺”

右侧面板现在的信息价值很高，但展示方式偏“结果罗列”。

#### 现在的问题

- 当前知识、是否命中、工具调用、可追踪状态全部同级展示
- 信息虽完整，但没有形成“先摘要、后细节”的节奏
- 用户理解成本高，且容易觉得是一个调试面板

#### 建议方向

右侧面板应该做成**渐进披露**：

- 默认只显示摘要：命中情况、工具调用状态、追踪状态
- 展开后再看详细来源、工具细节、检索命中列表
- 面板顶部加“当前回答概览”，让用户先知道“这次回答是什么状态”
- 右侧面板可以在无需要时折叠成窄栏，给主消息区让出空间

## 4. 我会怎么改：产品级优化原则

### 4.1 主原则

1. **聊天优先**：所有视觉设计都要服务消息流和输入动作。
2. **辅助信息二级化**：验证、流程、工具、引用默认折叠或轻展示。
3. **结构化内容独立化**：长文本、代码、结果卡、引用卡不要混在一层。
4. **渐进披露**：先给结论，再给证据，再给执行细节。
5. **状态显性化**：加载、流式、失败、停止、重试、空状态都要讲人话。
6. **减少选择负担**：把高频动作前置，低频动作收纳。

### 4.2 视觉气质目标

目标不是做得“酷”，而是做得更像一个**专业、稳定、轻负担、愿意反复使用**的产品。

可以把目标理解为：

- 从“后台系统感” → “专业助手感”
- 从“表格/面板拼接” → “内容工作区”
- 从“信息堆叠” → “信息编排”

## 5. 详细优化方案

### 5.1 整体布局改造

### 目标布局

建议把页面拆成三层：

- **左侧：会话导航**
- **中间：主聊天区**
- **右侧：回答概览/引用/工具信息**

但要注意：**右侧不是默认主内容**，而是“可收起的辅助区”。

### 具体建议

#### 左侧会话区

- 宽度略收窄，避免抢主视野
- 头部增加搜索和新会话按钮
- 会话条目简化为标题 + 最近摘要 + 时间
- 支持 pin / archive / delete，但默认不露出太多动作
- 选中态做得更“稳”，不是靠大面积蓝底

#### 中间主聊天区

- 让中间区在视觉上更像“主舞台”
- 消息流宽度适中，避免过宽导致阅读疲劳
- 每条消息留白更统一，减少上下挤压感
- 顶部流程条缩成轻量状态条，不要喧宾夺主

#### 右侧信息区

- 默认收缩为摘要视图
- 支持“固定展开 / 自动收起 / 仅在回答后展开”三种状态
- 只保留用户当下最关心的 3-4 个指标

---

### 5.2 会话列表优化

### 需要解决的问题

- 视觉噪音高
- 选中态不够精致
- 操作入口太显式
- 列表缺少内容感

### 设计建议

1. **增加会话摘要**
   - 最近一句话自动截断
   - 让用户一眼知道这个会话在聊什么

2. **强化选中态**
   - 用背景、边框、轻阴影、左侧标识条组合，而不是单纯底色变化

3. **收纳次要操作**
   - 重命名、删除、归档放进 hover menu
   - 减少静态界面上的按钮密度

4. **区分常用会话与历史会话**
   - 置顶、最近使用、收藏分组
   - 减少用户找会话的成本

5. **补空态**
   - 空会话列表时给出“新建对话 / 导入知识 / 查看示例”的引导

---

### 5.3 消息展示优化

### 需要解决的问题

- 消息间层次不够清晰
- assistant 的内容区阅读感不够强
- 工具、引用、反馈、复制等辅助动作都在抢注意力

### 设计建议

#### 用户消息

- 保持简洁、轻量、明显的右对齐或蓝色主题
- 不要做得太“卡片化”，避免喧宾夺主

#### 助手消息

- 左对齐，容器更像内容卡片
- 标题/正文/代码块/引用按层级排版
- 长文本保持较好的行宽，避免横向过长

#### Markdown / 代码块

- 代码块采用独立容器，支持复制按钮悬浮
- 引用、列表、表格等保持统一的阅读节奏
- 流式输出时避免排版跳动，保留稳定高度

#### 工具调用 / 引用来源

- 默认折叠
- 展开后显示结构化列表
- 工具成功/失败用更轻量的状态标签，不要让它看起来像错误日志

#### 消息动作条

建议把动作分层：

- 高优先级：复制、重新生成、继续
- 次优先级：反馈、有用/无用
- 危险动作：删除，明确红色与确认态

---

### 5.4 输入区（Composer）优化

### 目标

让用户一眼明白：**这里就是开始下一轮对话的地方。**

### 设计建议

1. **更强的输入焦点**
   - focus 时边框高亮、阴影增强
   - 输入框有明显“激活”状态

2. **动作分层**
   - 主动作：发送
   - 次动作：附件 / 上传 / 快捷 prompt
   - 低频动作：停止生成、更多菜单

3. **更好的空态引导**
   - 提供 2-4 个可点击示例问题
   - 示例问题最好贴近真实场景，而不是抽象问候

4. **输入辅助文案优化**
   - 文案不要太技术化
   - 例如：`输入问题，Enter 发送，Shift+Enter 换行`
   - 如支持文件或知识库，提示要更明确

5. **发送/停止状态切换清晰**
   - 生成中时显示停止
   - 停止后能明确继续 / 重试 / 重新生成

---

### 5.5 右侧信息面板优化

### 面板信息建议分 4 个区块

1. **本次回答概览**
   - 回答状态
   - 是否命中知识库
   - 是否调用工具
   - 是否可追踪

2. **引用来源**
   - 文档名称
   - 命中数量
   - 展开查看 chunk / 来源列表

3. **工具调用**
   - 工具名
   - 成功/失败
   - 耗时
   - 折叠查看详细参数

4. **调试/追踪信息**
   - Run ID
   - Trace 状态
   - 链路跳转入口

### 关键原则

- 默认只给摘要
- 细节需要展开
- 把“操作性信息”与“阅读性信息”分开

---

### 5.6 状态系统优化

现在最需要补的是“状态统一”。一个产品感强的聊天页，必须让用户清楚知道每一步发生了什么。

### 必备状态

1. **空会话状态**
   - 说明可以做什么
   - 给示例 prompt
   - 给文件/知识库入口

2. **生成中状态**
   - 让 streaming 有明显反馈
   - 避免用户重复点击发送

3. **停止状态**
   - 明确提示内容不完整
   - 提供继续、重试、重新生成

4. **失败状态**
   - 错误要可读
   - 说明原因 + 下一步建议

5. **无知识命中状态**
   - 不能只说“未命中”
   - 应该提示用户是否要导入文档、改问法、切换知识库

6. **无工具调用状态**
   - 不应该像异常
   - 只需要轻提示即可

7. **可追踪状态**
   - 明确显示 run / trace 是否可点击复盘

---

### 5.7 微交互优化

### 建议补齐的细节

- 当前会话 hover 时显示更温和的操作入口
- 消息复制成功后给短暂 toast 或状态反馈
- 工具折叠/展开有过渡动画
- 回到底部按钮在用户上滑后清晰出现
- 滚动位置不要因为流式输出而强行把用户拽回底部
- 删除、重试、继续、重新生成等危险或关键动作必须有确认与解释

### 交互目标

**让用户觉得“稳”、“顺”、“不会丢上下文”。**

---

### 5.8 可访问性与可用性

虽然这是内部/企业类产品，但仍然建议把基础可访问性做好。

- 按钮都有明确 aria-label
- 色彩对比满足可读性
- 仅靠颜色区分状态时，必须辅以文字或图标
- 键盘操作要顺畅：Tab、Enter、Esc、方向键
- 输入框和按钮的 focus 样式要清晰

---

## 6. 结合当前代码，建议怎么落地

### 6.1 优先改哪些文件

1. `frontend/src/pages/Chat/index.tsx`
   - 改页面布局和状态编排
   - 做 sidebar / right panel 的折叠逻辑
   - 优化 composer 和快捷 prompt

2. `frontend/src/pages/Chat/components/MessageBubble/index.tsx`
   - 调整气泡结构
   - 优化工具、引用、反馈、失败态的展示层级

3. `frontend/src/styles.less`
   - 统一设计令牌
   - 调整圆角、留白、阴影、状态色
   - 重新定义聊天区、侧栏、输入区的视觉权重

4. `frontend/src/pages/Chat/components/SessionItemView`
   - 简化会话条目
   - 增加摘要、状态、置顶态

### 6.2 不建议先做的事

- 不要先大改业务逻辑
- 不要先把所有功能继续堆进右侧面板
- 不要先加更多按钮
- 不要先做花哨动效

优先顺序应该是：

**布局主次 > 信息分层 > 状态统一 > 微交互润色**

## 7. 建议的实施排期

### P0：快速拉升观感，1-3 天

目标：先把“很拉”的感觉降下来。

- 调整整体留白和间距
- 降低边框和分割线存在感
- 优化消息卡片、输入框、会话列表的基础样式
- 强化 current session / message / composer 的视觉主次
- 统一 loading、empty、error 的基础样式

**验收标准：**
- 页面第一眼更像聊天产品
- 输入框更像“主动作区”
- 视觉噪音明显下降

### P1：重排信息架构，3-5 天

目标：把页面从“工作台”拉回“聊天页”。

- 侧栏收窄或可折叠
- 右侧验证信息改为可收起面板
- 顶部流程条轻量化
- 主聊天区扩大
- 会话列表信息压缩

**验收标准：**
- 主聊天区成为绝对视觉中心
- 辅助信息不再抢主流程

### P2：补齐产品级状态，5-8 天

目标：让用户感受到“稳定、清晰、可追踪”。

- 空态、流式、失败、停止、重试状态完善
- 工具调用和引用来源做渐进披露
- 消息动作分层
- composer 交互更明确

**验收标准：**
- 用户能理解每个状态为什么出现
- 不会因为信息过多而迷失

### P3：做细节打磨与指标验证，持续迭代

目标：验证改版是否真正提升可用性。

- 观察会话启动率
- 观察单轮对话完成率
- 观察重试/回到底部/复制/引用展开等行为
- 观察用户对右侧面板的使用率

---

## 8. 建议的指标

建议至少跟踪以下指标，判断 UI 改版是否有效：

1. **首次进入后 30 秒内发起第一条消息的比例**
2. **输入框 focus 后 10 秒内发送成功率**
3. **用户是否经常点击“回到底部”**
4. **工具调用/引用面板展开率**
5. **消息复制率、重新生成率、重试率**
6. **空会话到首条消息转化率**
7. **会话切换频率与平均停留时长**

这些指标能帮助判断：
- 用户是否更容易开始对话
- 用户是否更愿意继续追问
- 用户是否真的在使用辅助信息，而不是被它们干扰

## 9. 最终建议

如果只做一句话级别的改版目标，我会把它定义为：

> **把聊天页从“功能型控制台”改成“对话型工作台”。**

具体落点就是：

- **聊天区最大、最清楚**
- **侧边信息辅助而不是主导**
- **输入框是最强行动入口**
- **结构化结果独立承载**
- **所有状态都能被解释**
