# 产品化详细路线图（Productization Roadmap）

> 更新时间：2026-09-01
>
> 目标：把当前“功能完备但偏平台内核”的项目，推进成**可售卖、可交付、可持续运营**的企业级 Agent 平台。
> 本文档偏“战略 + 里程碑 + 验收口径”；更细的当前功能优化清单见 `feature-optimization-plan.md`。

## 1. 先看竞品：他们到底做对了什么

> 这里不是简单抄功能，而是提炼产品方法论。

| 竞品 | 核心强项 | 对本项目的直接启发 |
|---|---|---|
| LangSmith | Prompt / Trace / Eval / Experiment 连成闭环 | 发布不只做“上线”，而是做“可回放、可对比、可验证”的质量闭环 |
| Langfuse | API-first 的观测、Prompt 版本、Dataset、Evaluation | 所有运行数据都应该能回流到评测集，形成持续优化飞轮 |
| Dify | 低门槛 onboarding、Publish Update、插件生态 | 产品必须把“第一次成功”缩短到几分钟，并提供模板/生态 |
| Azure AI Foundry | 企业治理、可观测、评测、权限与合规 | 面向企业客户必须强化 IAM、审计、SLA、可追责与运维接入 |
| OpenAI 平台 | 简洁原语、评测、模型/工具抽象 | 平台能力要尽量标准化，减少“页面化的私有逻辑” |

### 1.1 竞品共同点

1. **从“功能”转向“流程”**：都把 prompt、trace、eval、deploy 连接成用户闭环。
2. **从“单次调用”转向“持续优化”**：线上数据会进入离线评测或实验系统。
3. **从“能用”转向“可治理”**：权限、环境、版本、审计、回滚都被产品化。
4. **从“工具”转向“平台”**：允许模板、连接器、插件、API、SDK、Webhook 扩展。

### 1.2 我们的差异化定位

本项目不建议做成另一个“通用聊天机器人搭建器”。更适合的定位是：

> **企业 Agent 发布与治理平台**

也就是把以下能力做深：

- 版本治理：draft / publish / canary / rollback
- 质量治理：contract check / regression / eval / replay
- 风险治理：RBAC / approval / audit / sandbox
- 成本治理：budget / quota / usage / anomaly
- 运维治理：backup / restore / health / queue / retention

这条路线最容易形成企业客户愿意付费的差异点。

## 2. 现状摘要：我们已经有什么

| 域 | 现状 | 产品判断 |
|---|---|---|
| 运行时 | Agent run、状态机、checkpoint、恢复、取消、重放 | 已经具备平台内核，不是 demo 级 |
| 发布治理 | 契约检查、回归、灰度、回滚、审批 | 是当前最强卖点，应该继续加深 |
| 知识与检索 | 入库、分块、混合检索、引用来源 | 已能支撑企业知识问答，但体验和调参需增强 |
| 评测 | 基准集 / 回归 / 安全评测 | 有基础，但还缺“实验管理 + 标注闭环” |
| 成本与审计 | 用量聚合、审计导出、事件流 | 能做治理，但需要更强的报表和告警 |
| 多租户与权限 | 租户、用户、角色、策略 | 基础已具备，但仍需完善企业身份体系 |
| 前端 | 控制台覆盖多数模块 | 功能覆盖足够，但流程引导和体验一致性要提升 |
| 交付 | Docker / Caddy / 文档 / 冒烟脚本 | 具备交付地基，但还没形成标准化交付包 |

## 3. 产品化目标拆解

### 3.1 北极星指标

产品化阶段不再只看“功能有没有”，而看以下指标：

- **TTV（Time to Value）**：用户从登录到第一次成功对话/发布的时间
- **Release Success Rate**：发布成功率、回滚率、canary 命中率
- **Evaluation Coverage**：发布前覆盖了多少关键场景/坏案例
- **Governance Coverage**：审批、审计、RBAC、quota、retention 是否全链路可用
- **Operational Readiness**：备份恢复、告警、健康检查、队列治理是否可交付
- **Cost Visibility**：能否清楚回答“这个租户/Agent 为什么贵”

### 3.2 产品原则

1. **先治理，后扩展**：没有权限、审计、配额、回滚的扩展都不能先于治理。
2. **先闭环，后生态**：先把“创建 → 运行 → 评测 → 发布 → 监控 → 回滚”做稳，再做 Marketplace。
3. **先默认可用，再可配置**：初始模板必须能直接跑通，不依赖用户理解全部参数。
4. **先可解释，再自动化**：所有自动动作都要有原因、证据、记录。
5. **先企业通用，后行业定制**：避免把产品做成单项目项目制代码堆。

## 4. 详细路线图

### Phase 0 · 上线门禁与底座加固（P0）

**目标**：把“不能上生产”的风险项清零，确保平台可安全交付。

| 子任务 | 交付物 | 验收标准 |
|---|---|---|
| 强制认证与默认密钥整改 | 生产环境无 token 不可访问；默认 secret 启动直接失败 | 未认证请求统一 401；prod 配置校验失败即阻断启动 |
| Secret / 凭据体系 | KMS / 外部 Secret Manager 接入指南与实现 | 凭据不落明文、不随重启丢失 |
| API 错误路径清理 | API 404 / 业务错误不再被 SPA fallback 掩盖 | 前后端联调可准确定位接口问题 |
| 生产启动校验 | 配置、数据库、Redis、LLM 依赖预检 | 启动时可读出明确缺失项 |
| 安全基线复核 | SSRF、沙箱、上传、审计、脱敏复查 | 红线项有测试和文档 |

**建议优先级**：最高。这个阶段做完，产品才具备“外部可见的可信底座”。

---

### Phase 1 · 首次成功与身份闭环（P0 / P1）

**目标**：让新客户从“拿到系统”到“第一次跑通”尽可能快。

| 子任务 | 交付物 | 验收标准 |
|---|---|---|
| Onboarding Wizard | 进入系统后按步骤完成租户、用户、模型、知识、对话、发布 | 10 分钟内完成第一次成功 |
| 用户生命周期 | 创建 / 邀请 / 禁用 / 重置密码 / 首登强制改密 | 管理员可独立完成日常运维 |
| 租户生命周期 | 新建租户、默认角色、默认策略、隔离校验 | 租户间数据 / 审计 / 配置不串 |
| 角色模板 | Admin / Operator / Reviewer / Viewer 等预设角色 | 客户不必从零配置 RBAC |
| OIDC / SSO 打通 | 至少 OIDC，SAML 作为后续企业版能力 | 企业身份源可以接入 |
| 配额可视化 | 用户数、Agent 数、run 次数、token、存储、连接器 | 超限前可见，超限时有明确错误 |

**产品目标**：把“管理员手工解释平台”变成“用户按引导自助上手”。

---

### Phase 2 · 质量闭环与发布治理深化（P1）

**目标**：把平台的旗舰能力做成“可重复、可比较、可审计”的质量流水线。

| 子任务 | 交付物 | 验收标准 |
|---|---|---|
| Prompt Registry | Prompt 版本、标签、对比、回滚 | prompt 变更可追溯 |
| Dataset / Eval 管理 | 黄金集、坏案例、对抗集、行业模板 | 评测集可复用、可迭代 |
| Experiment 面板 | 同一 dataset 上比较不同模型/提示词/检索配置 | 能一眼看出提升或退化 |
| 发布门禁增强 | contract check、regression、canary 三段式联动 | 发布不是“点按钮”，而是“过门禁” |
| Replay / Compare 深化 | run 对比、参数 diff、证据链回放 | 能定位“为什么这次不一样” |
| 人工标注闭环 | 线上 trace 反馈回流 dataset | 线上失败场景能持续变成评测样本 |

**产品目标**：把“发布”升级成“质量实验 + 门禁决策”。

---

### Phase 3 · 企业运维与可靠性交付（P1 / P2）

**目标**：让平台具备真正交付到客户环境的能力。

| 子任务 | 交付物 | 验收标准 |
|---|---|---|
| 备份 / 恢复标准化 | 备份策略、恢复演练、RPO/RTO 文档 | 客户能按文档自助恢复 |
| 监控与告警 | health / queue / cost / model / release 告警 | 异常能被及时发现 |
| 审计与合规 | 审计导出、保留期、清理策略、证据归档 | 合规检查可落地 |
| 容量规划 | run 并发、LLM 请求、向量检索、队列吞吐 | 有明确容量边界 |
| 沙箱隔离升级 | Docker / gVisor / 网络隔离策略 | 高风险工具不能越界 |
| 多实例与 HA | 队列、锁、幂等、恢复、健康探测 | 单机故障不影响整体业务 |

**产品目标**：把“开发态可跑”升级成“生产态可运营”。

---

### Phase 4 · 商业化与生态（P2）

**目标**：让产品不仅能交付，还能规模化销售。

| 子任务 | 交付物 | 验收标准 |
|---|---|---|
| 套餐与配额强制 | 基础版 / 专业版 / 企业版配额落地 | 报价、配置、代码一致 |
| 计量与账单 | usage / token / run / storage / connector 账单口径 | 销售与产品口径一致 |
| 模板中心 | 官方模板 Agent / 模型 / 知识 / 发布流程 | 降低首次配置成本 |
| 连接器与工具市场 | MCP / 自定义工具 / Webhook / 插件目录 | 生态可扩展 |
| 交付包标准化 | Docker / Helm / 文档 / 脚本 / 支持包 | 复制部署成本下降 |

**产品目标**：让销售、交付、实施、支持都能围绕同一套产品能力协作。

## 5. 推荐节奏：12 周执行法

> 下面是一个偏实战的推进节奏，可按团队人力调整。

| 周期 | 重点 | 结果 |
|---|---|---|
| 第 1-2 周 | Phase 0 | 上线门禁清理完毕，生产风险项收敛 |
| 第 3-4 周 | Phase 1 | 首次成功路径跑通，账号/租户闭环成型 |
| 第 5-7 周 | Phase 2 | 评测、发布、回放、实验形成质量闭环 |
| 第 8-10 周 | Phase 3 | 运维、备份、告警、HA、沙箱加强 |
| 第 11-12 周 | Phase 4 | 套餐、模板、账单、交付包落地 |

## 6. 风险与依赖

| 风险 | 影响 | 缓解方式 |
|---|---|---|
| 认证 / 密钥整改影响兼容性 | 现有无 token 行为会变化 | 先改测试与文档，再收紧生产默认值 |
| 真实 LLM 引入非确定性 | 评测结果波动 | 先建立固定 dataset 和 baseline |
| 套餐化接线不完整 | 销售与产品口径不一致 | 先定义强制配额口径，再做展示页 |
| 多实例与 HA 改动面大 | 稳定性风险 | 分阶段推进，先保证幂等和恢复 |
| 沙箱隔离升级成本高 | 部署复杂度上升 | 提供默认安全策略与可选增强 |

## 7. 里程碑验收标准（Definition of Done）

### 7.1 产品级验收

- 新租户可在 10 分钟内完成第一次成功对话
- 新租户可在 30 分钟内完成一次“创建 → 测试 → 发布 → 回滚”的完整流程
- 管理员可独立完成用户、角色、权限、配额、审计、导出
- 评测结果能支撑发布决策，不是单独孤立页面
- 运营侧能看到成本、队列、健康、告警、保留期、恢复能力

### 7.2 工程级验收

- 生产配置校验 fail-fast
- 所有高风险操作都有确认、审批或审计
- 关键路径有自动化测试和回归脚本
- 文档、截图、控制台、API 口径一致
- 套餐、配额、权限、数据保留行为一致

## 8. 暂不建议投入的方向

1. **过早做复杂多端**：先把 Web 控制台打磨好，不急着原生 App。
2. **过早做过度行业化模板**：先做通用企业场景，再做行业方案。
3. **过早引入过多复杂工作流引擎**：当前已有核心编排能力，先把体验和治理做稳。
4. **过早追求“万能 Agent 平台”**：应收敛成“企业发布与治理平台”的清晰定位。
